# 昵称约束规格：仅可改一次 + 全局唯一

> 版本：v1.0　实施日期：2026-11-08
> 涉及：`cloudfunctions/login/`（nickname.js / index.js）、`pages/user`、`users` 集合

---

## 一、规则定义

| # | 规则 | 说明 |
|---|---|---|
| R1 | **首次设置不限次** | 从「无昵称」到「有昵称」算首次设置，**不消耗**修改机会。否则新用户一设昵称就被锁死，V4 写操作永远无法解锁 |
| R2 | **修改仅一次** | 已经有过昵称再替换，只能成功一次 |
| R3 | **全局唯一** | 任意两个用户的昵称不能相同 |
| R4 | **不区分大小写** | `Tom`、`tom`、` Tom ` 视为同一个昵称 |
| R5 | **幂等** | 提交的昵称与当前昵称完全一致时，直接返回成功，**不消耗**次数 |

R4 的理由：中文无大小写，但英文昵称若区分大小写，`Tom` 和 `tom` 肉眼难辨，等于给冒名留了口子。

## 二、字段设计（`users` 集合）

| 字段 | 类型 | 何时写入 | 说明 |
|---|---|---|---|
| `nickname` | string | 设置/修改昵称 | 归一化后的展示值（压缩空白、去首尾） |
| `nicknameKey` | string | 建档时 + 每次改昵称 | **唯一键**，见第三节 |
| `nicknameChangeCount` | number | 建档时置 0；修改成功后置 1 | 修改次数，首次设置不增 |
| `nicknameSetAt` | Date | 首次设置昵称 | 首次设置时间 |
| `nicknameChangedAt` | Date | 修改昵称成功 | 修改时间 |
| `nicknameConflict` | boolean | 迁移时写入 | 迁移中发现重名的标记，提示用户改名 |

**为什么次数要单独存字段**：用「`nicknameChangedAt` 是否存在」也能判断，但字段存在性在各版本数据里不可靠（老数据、手改数据），显式计数更稳，且能直接用于条件更新的并发控制。

---

## 三、唯一键设计（关键）

```
已设昵称：nicknameKey = 'n:' + 归一化小写昵称
未设昵称：nicknameKey = 'u:' + openid
```

**为什么要占位键**：如果未设昵称时留空，MongoDB 的唯一索引会把「字段缺失」都当成 `null`，多个空值互相冲突，索引根本建不起来。用 `u:openid` 占位，保证每个文档都有**唯一且永不与真实昵称冲突**的值（真实键统一 `n:` 前缀）。

归一化顺序：全角空格→半角 → 连续空白压缩为单空格 → 去首尾 → `toLowerCase()`。

## 四、后端校验逻辑（`login.updateProfile`）

按顺序执行，任一不通过立即返回：

| 步骤 | 校验 | 失败返回 |
|---|---|---|
| 1 | openid 存在、档案存在 | `UNAUTHORIZED` |
| 2 | 有 nickname 或 avatarUrl 至少一项 | `INVALID_PARAM` |
| 3 | `isValidNickname`：2–20 字、非纯数字、无控制字符 | `NICKNAME_INVALID` |
| 4 | 与当前昵称相同 → 幂等成功，直接返回 | — |
| 5 | `nicknameChangeState`：首次设置放行；已改过则拒 | `NICKNAME_CHANGE_USED` |
| 6 | 按 `nicknameKey` 查重（排除自己） | `NICKNAME_TAKEN` |
| 7 | 条件更新 `where({ openid, nicknameChangeCount: 读取时的值 })` | `updated !== 1` → `NICKNAME_CHANGE_USED` |
| 8 | 捕获唯一索引冲突（E11000） | `NICKNAME_TAKEN` |

## 五、并发处理

### 5.1 同一用户重复提交

场景：连点两次「保存」，或弱网重试。

**手段**：条件更新 + 次数计数。

```js
where({ openid, nicknameChangeCount: expectCount }).update({ ... })
```

两个请求都读到 `count = 0`，都试图写入；数据库保证只有一个 `updated === 1`，另一个得到 `updated === 0` → 返回 `NICKNAME_CHANGE_USED`。

**特例**：如果两次提交的是同一个昵称，第 4 步的幂等判断会提前命中，两次都返回成功且不消耗次数——这是期望行为。

### 5.2 两个用户抢同一个昵称

场景：A 和 B 同时把昵称改成「张三」。

**手段分两层**：

1. **预查重**（第 6 步）：只为给用户一个友好的即时提示，**不能作为最终保障**——两个请求可能同时通过查重。
2. **唯一索引兜底**：`users.nicknameKey` 建唯一索引后，后写入的那条会被数据库拒绝（E11000），代码捕获后同样返回 `NICKNAME_TAKEN`。

> ⚠️ **必须在云开发控制台给 `users.nicknameKey` 建唯一索引**，否则并发窗口仍然存在。代码层查重只是体验优化，不是安全边界。

### 5.3 首次设置与修改的并发

首次设置不写 `nicknameChangeCount`，所以条件更新仍以旧值（0）为条件；两次并发的「首次设置」都写相同字段，结果一致，无副作用。

## 六、错误码与文案

| 错误码 | 触发条件 | 用户提示（原文） | 前端处理 |
|---|---|---|---|
| `NICKNAME_INVALID` | 长度不在 2–20、纯数字、含控制字符 | 「昵称需 2-20 个字，不能是纯数字或特殊字符」 | Toast，停留弹窗 |
| `NICKNAME_TAKEN` | 唯一键冲突 | 「这个昵称已经有人用了，换一个吧」 | Toast，停留弹窗 |
| `NICKNAME_CHANGE_USED` | 已用过修改机会 | 「昵称只能修改一次，你已经用过了」 | Toast，按钮置灰 |
| `UNAUTHORIZED` | 未登录 / 档案不存在 | 「请先登录」 | 走统一登录引导 |

前端「我的」页三种状态：

| 状态 | 文案 | 交互 |
|---|---|---|
| 未设昵称 | 「设置昵称」 | 可点 |
| 已设、未改过 | 「修改昵称（仅一次）」+ 副标「昵称还可修改 1 次」 | 可点 |
| 已改过 | 「修改昵称」+ 右侧「已用完」，整行半透明 | 点击只 Toast，不发请求 |

## 七、迁移方案

老数据没有 `nicknameKey` / `nicknameChangeCount`，直接建唯一索引会因为「多个文档缺少该字段」失败。

### 7.1 懒迁移（自动，无需干预）

`register` 建档或重复登录时，若发现字段缺失，自动补齐：
- `nicknameChangeCount` 缺失 → 置 0
- `nicknameKey` 缺失 → 按当前昵称计算（无昵称则用 `u:openid`）

### 7.2 批量迁移（建索引前必须跑）

`login` 云函数新增 `migrateNicknameKey` 动作，**仅 `ADMIN_OPENIDS` 白名单可调**，默认 dryRun。

```json
// 1) 先看报告，不写库
{ "action": "migrateNicknameKey", "data": {} }

// 2) 确认无误后真正落库
{ "action": "migrateNicknameKey", "data": { "apply": true } }
```

返回：`{ total, patched, conflicts: [{ openid, nickname, conflictWith }], dryRun }`

**冲突策略**：按 `createdAt` 升序扫描，先注册者保留昵称键；后来者 `nicknameKey` 退回 `u:openid` 并打 `nicknameConflict: true`，其昵称仍可正常显示，但下次修改时必须换名（改名不消耗次数）。

### 7.3 建索引（迁移之后）

云开发控制台 → 数据库 → `users` → 索引管理 → 添加索引：

| 索引名 | 字段 | 属性 |
|---|---|---|
| `uniq_nickname` | `nicknameKey` 升序 | **唯一** |

顺序不能反：**先迁移，后建索引**。反了会因为空值冲突建不上。

## 八、测试用例

自动化：`node scripts/test-nickname.js`（26 条，覆盖归一化、合法性、唯一键、次数状态、三场景）

### 关键三场景（端到端）

| # | 场景 | 操作 | 预期 |
|---|---|---|---|
| T1 | **首次修改成功** | 新用户登录（昵称空）→ 设置「小明」 | 成功；`nicknameChangeCount` 仍为 0；`nicknameSetAt` 有值 |
| T2 | **二次修改被拒绝** | 接着再改成「小红」 | 成功（这是那唯一一次修改）；`nicknameChangeCount` = 1。**第三次**再改才被拒，返回 `NICKNAME_CHANGE_USED` |
| T3 | **昵称重复被拒绝** | 另一个账号设置已被占用的「小明」 | 返回 `NICKNAME_TAKEN`，提示「这个昵称已经有人用了」 |

> T2 的措辞需要说清楚：规则是「首次设置不占次数，之后可改一次」，所以从空→有→再改，一共能设两次不同昵称，第三次才锁。如果你要的是「总共和当前不同的只能设一次」（即空→有也算用掉），把 `nicknameChangeState` 里 `isFirstSet` 分支去掉即可，测试用例 `未设昵称 → 首次设置，不计次数` 同步改成拒绝。

### 其他边界

| # | 场景 | 预期 |
|---|---|---|
| T4 | 大小写不同：已有 `Tom`，改 `tom` | `NICKNAME_TAKEN` |
| T5 | 带空格：提交 ` Tom ` | 归一化为 `Tom`，命中 T4 |
| T6 | 幂等：把昵称「原样再提交一次」 | 成功且不消耗次数 |
| T7 | 连点两次保存 | 只有一次成功，另一次幂等或 `NICKNAME_CHANGE_USED` |
| T8 | 两个账号并发抢同一昵称 | 一个成功，另一个 `NICKNAME_TAKEN`（依赖唯一索引） |
| T9 | 昵称填 1 个字 / 21 个字 / 纯数字 | `NICKNAME_INVALID` |
| T10 | 修改昵称时顺带换头像 | 昵称次数照常扣减，头像更新不影响判定 |
| T11 | 老用户（无 nicknameChangeCount）首次改名 | 视为未改过，允许 |

## 九、已知限制

1. **唯一性最终依赖索引**。未建唯一索引时，5.2 的并发窗口存在。文档已标注，但自动化无法验证索引是否真的建了。
2. **未做敏感词/内容安全校验**。昵称是公开可见字段，P0-1 的内容安全接入后应把 `msgSecCheck` 也加到昵称上。
3. **未支持昵称释放**。用户注销后昵称仍被占用。若要释放，需在注销流程里把 `nicknameKey` 改回占位键。
4. **emoji 昵称**。当前允许 emoji（长度按码点算），唯一性按 emoji 原样比较。不同厂商的同形 emoji 可能被判为不同，属可接受误差。
